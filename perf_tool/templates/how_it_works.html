How it works

Full detail (setup, nginx wiring, extending it) lives in PERF_TOOL.md in the repo — this page is just the part that matters while reading a result: what each number actually measures.

Wall time

Measured in the tool itself, wrapped directly around the HTTP call(s) that make up the scenario. For an upload, the clock doesn't stop at the initial 201 Accepted — it keeps running while the tool polls /api/v2/resource-service/execution-status/<id> until the async pipeline reports finished or failed. This is real end-to-end time, not just "how long until the server said OK."

min / avg / median / max — how the four numbers are computed

Every metric on this page (wall time, xact_commit Δ, DB queries) is measured once per iteration, giving a list of raw numbers — e.g. running a test 5 times might give wall times [0.82, 0.79, 1.34, 0.81, 0.80] seconds. That list is then summarized four ways:

  • min — the single fastest/lowest iteration (min()). In the example: 0.79. Tells you the best case this instance is capable of, right now.
  • avg (average / mean) — all the values added together, divided by the iteration count (Python's statistics.mean()). In the example: (0.82+0.79+1.34+0.81+0.80)/5 = 0.912. This is the headline number — the one to trust when comparing two runs, and the one both the summary cards and the downloadable PDF report lead with. Averages get pulled hard by outliers: that one slow 1.34 iteration alone moved the average up by about 0.09s from what the other four would suggest on their own.
  • median — the middle value once the list is sorted (statistics.median()); sorted, the example is [0.79, 0.80, 0.81, 0.82, 1.34], so median = 0.81. Unlike the average, one outlier can't drag the median far — that's exactly why it's shown side by side with avg: if avg and median are close, the run was consistent; if avg is noticeably higher than median, one or two iterations were unusually slow (worth checking the per-iteration table for which one, and why).
  • max — the single slowest/highest iteration (max()). In the example: 1.34. Tells you the worst case actually observed — useful for spotting a scenario that's occasionally, not consistently, expensive (a GC pause, a cold cache, a celery worker busy with something else at that exact moment).

With only 1 iteration all four numbers are identical (there's only one value to summarize) — which is also the reason a single run isn't a measurement: there's no way to tell whether that one number was typical or a fluke. 3-5 iterations is usually enough to see the difference between min/median/max start to separate out and tell you something.

"DB queries (this request only)" — the noise-free number

Everything above (xact_commit, tup_inserted/updated/deleted, the per-table breakdown) reads Postgres's own counters, which are whole-database — there's no built-in Postgres view that tracks cumulative query counts per session or per request, only per database or per table, both shared with everything else happening on the instance.

To get a real per-request number, GeoNode itself now counts its own queries: geonode.base.middleware.RequestQueryStatsMiddleware wraps every request in connection.execute_wrapper() (a Django hook that counts queries and timing regardless of DEBUG) and returns the result as X-DB-Query-Count / X-DB-Query-Time-Ms response headers. perf_tool reads these headers on every HTTP call a scenario makes and sums them — this number cannot be polluted by another user's request, a celery beat tick, or anything else on the instance, because it's counted inside the exact request/response cycle the tool triggered.

Off by default (EXPOSE_DB_QUERY_STATS_HEADER=False) since it reveals internal query volume in a response header — turn it on for the target instance's Django/celery services to see it. Shows as 0 when it's off; everything else on this page keeps working either way.

xact_commit Δ, tup_inserted/updated/deleted Δ

A snapshot of Postgres's own pg_stat_database counters is taken immediately before and immediately after the action runs, on a connection with autocommit on (so each snapshot is fresh, not served from a cached transaction view — Postgres caches these views per-transaction by default, which silently gives zero for both snapshots if you don't watch for it). The delta is how many transactions Postgres committed, and how many rows it inserted/updated/deleted, while the action ran.

The honest caveat: these are whole-database counters, not scoped to one HTTP request. If anything else is hitting the same Postgres instance while a test runs — another user, a celery beat tick, a concurrent test — it shows up in the delta too. That's inherent to the method, not a bug. The fix: run against a quiet instance when precision matters, run several iterations and look at the average, and prefer relative comparisons (before a fix vs. after) over trusting one absolute number. That's what the iteration/average and compare features are for.

seq_scan Δ / idx_scan Δ / inserted Δ / updated Δ / deleted Δ (per-table breakdown)

The same before/after snapshot approach as xact_commit Δ above, but read from pg_stat_user_tables instead of pg_stat_database — a separate before/after delta per table, for a fixed list of GeoNode-relevant tables (TRACKED_TABLES in perf_tool/db_stats.py; add to it if you're chasing a table not already tracked).

This one isn't min/avg/median/max — it's summed across every iteration of the run. Where wall time and xact_commit answer "what's typical for one run," the per-table breakdown answers "how much did this whole test push through that table, all iterations combined" — useful for the same reason a bulk-insert fix is judged on total rows written, not an average per attempt. Worked example: a 3-run test where each iteration updates base_resourcebase a different number of times —

  • iteration 1: n_tup_upd delta = 28
  • iteration 2: n_tup_upd delta = 26
  • iteration 3: n_tup_upd delta = 30

The table on the result page shows updated Δ = 84 (28+26+30) for base_resourcebase — the total, not 28 (the average of ~28). Dividing the shown total by the iteration count gets you back to a rough per-run average if that's what you want instead.

seq_scan is a full table scan; a rising count on a table that should be indexed is a red flag. idx_scan is an index scan — generally the cheap, wanted way to read a table. Compare the two to see whether a query is actually using an index. Rows are sorted by total activity (highest first) so the table that moved the most during the test is always at the top. This exact table (well, its manual precursor — one before/after `psql` query at a time) is what originally found the 64 base_resourcebase updates in one dataset upload, and the redundant ContactRole lookups per resource, documented in PERFORMANCE_FIX_PLAN.md.

Top queries (pg_stat_statements)

Only shown when the pg_stat_statements extension is installed and readable — exact SQL text, call count, and total execution time, diffed the same before/after way. Falls back silently to the per-table breakdown above on any instance where the extension isn't available; no superuser is required to read it once it's installed.
